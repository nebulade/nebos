Boot & firmware

Three ways into the same kernel.

A legacy BIOS floppy, a dual-boot USB image under UEFI, and a live serial or network reload all converge on kernel_entry. They must agree on three things: the low-memory boot structures, the rootfs pack location, and a 32-bit flat protected-mode environment.

Three paths, one entry point

The boot code is deliberately split by execution mode. The BIOS path starts in 16-bit real mode, the UEFI path starts in 64-bit long mode, and the kexec path starts in the running 32-bit kernel. All three end at kernel_entry in entry.S, which immediately re-points ESP at the new image's own boot stack before calling kernel_main.

BIOS path

boot.S — the 512-byte boot sector

The boot sector carries a FAT16 BPB, loads the contiguous kernel directly after itself to 0x7E00, and jumps there. Floppy drives use CHS; fixed disks use INT 13h AH=42h (EDD LBA). The sector count and the rootfs LBA are patched into the boot sector by the Makefile.

On the USB image, mbr.S runs first and loads the active partition's boot sector at LBA 63. From there the path is identical.

vesa_stage.S — the real-mode setup

The VESA stage is the busiest piece of the legacy chain. It runs in real mode at 0x7E00 and performs five jobs:

  1. Probe the INT 15h E820 memory map into 0x1000.
  2. Read the NBROOT1 rootfs header at the boot sector's pack_lba field.
  3. Stage the compressed pack in the low gap 0x60000..0x9FBFF, using 16 KB staging chunks at 0x3000 and rep movsb. No protected-mode BIOS call is required.
  4. Pick the best VBE mode: at least 16 bpp, a linear framebuffer, it must fit the card's VRAM, and the width must be at most 1280 pixels. Mode information is written to 0x600; the 12-dword boot-info block goes to 0x500.
  5. Enable A20, enter protected mode, copy the pack to 0x900000 above the 8 MB VGA-shadow reserve, rewrite the boot-info pack address, and jump to kernel_entry.

The staging gap is why the compressed pack has a hard cap of 0x3FBFF (~255 KB), ending below the EBDA at 0x9FC00. The kernel image itself must stay below the same gap, which kernel.ld enforces with link-time assertions.

Why copy the pack again? The low gap is temporary: the kernel BSS and boot stack may extend past 0x60000. Moving the pack to 0x900000 before kernel_main keeps it safe until ramfs.c takes a private page-allocated copy and releases the boot region.

UEFI path

efi/main.c is a freestanding x86-64 PE32+ application built with x86_64-w64-mingw32-gcc. It does not execute any of the legacy boot chain. Instead it:

  1. Selects a GOP mode with BGRX or RGBX 32bpp, width at most 1280, pitch × height at most 8 MB, and a framebuffer below 4 GB.
  2. Calls GetMemoryMap and converts the firmware map into the kernel's E820 format at 0x1000.
  3. Stages the kernel image below 4 GB and writes the boot-info and framebuffer blocks.
  4. Calls ExitBootServices, copies the embedded rootfs pack to the top of RAM below 128 MB, and copies a 192-byte trampoline to 0x800.
  5. Leaves IA-32e mode (clears CR0.PG, EFER.LME, CR4.PAE/PGE/PCIDE/SMEP/SMAP/LA57), copies the kernel to 0x7E00, and jumps to kernel_entry.

efi/payload.S embeds the compressed kernel, the gzip rootfs pack and the trampoline inside BOOTX64.EFI, so the ESP is self-contained. Secure Boot must be off; the loader is unsigned.

No GOP, no video. If the loader cannot satisfy the mode constraints it still boots, but the kernel starts headless and only the serial log is available.

kexec path

kexec is the normal development loop: it replaces the running kernel without rebooting, reflashing or re-running the firmware. The framebuffer and its mode stay in place; only the image changes.

  • Serial. The WM loop watches the COM1 ring buffer for the KXE2 magic. The header carries entry, kernel size, pack size and a checksum; pack_size == 0 keeps the running rootfs.
  • Network. The same transfer runs over UDP port 19288 with the KXN2 magic. The board acknowledges every datagram with the next expected offset and verifies a 32-bit checksum.
  • Runtime pack only. KXNP over serial or network replaces /ramfs in place without touching the kernel.

Before jumping, kexec.c calls smp_stop_aps(): every AP receives an INIT and is parked in the wait-for-SIPI state before the trampoline overwrites the kernel they were executing. The trampoline runs with interrupts off, resets sched_lock (an AP may have been inside a scheduler critical section), and jumps to kernel_entry.

Because entry.S re-points ESP before any stack use, a reload between builds with different memory maps cannot inherit a stale stack inside the new image.

Handoff contract

bootinfo.h defines the 12-dword block at 0x500. The checksum is chosen so all twelve words sum to zero; that keeps stale low memory from being mistaken for a valid block after a kexec or legacy boot.

OffsetFieldMeaning
+0magic0x4E425349 ("NBSI")
+4versionCurrently 2.
+8checksumMakes the 12-word sum zero.
+12rsdpACPI RSDP physical address; zero means scan.
+16flagsEFI, RGBX pixel order, retained network config.
+20pack_addrBoot-time rootfs pack address, zero if none.
+24pack_sizeExact gzip or raw pack byte count.
+28reserved[5]Reserved; the kexec path stores retained IP/mask/gateway/DNS here.

The framebuffer block at 0x600 is a struct vga_boot_fb_info (vga.h): valid flag, LFB base, pitch, width, height, bpp and the RGBX flag. The E820 map at 0x1000 is a struct e820_map (mm.h): magic, count and up to 32 entries.

Disk image layout

The build produces several images from the same boot sector, kernel and rootfs. The layouts are intentionally conservative: the first 1.44 MB must remain readable by a CHS-only BIOS.

Kernel init order

kernel_main is a single linear bring-up. The order is constrained by what each step needs: GDT/TSS before current_proc(), paging before ACPI table access, process setup before the PIT can context-switch, and a ticking timer before AP bring-up can time out.

  1. Clear BSS; initialise the boot console straight into the framebuffer.
  2. Bring up COM1 and the network-console ring buffer.
  3. Install the GDT/TSS and per-CPU GS base.
  4. Parse E820, build the frame bitmap and initialise kmalloc.
  5. Enable paging; keep a RAM copy of the boot log; enable SSE state if present.
  6. Parse ACPI/MADT; initialise I/O, power, idle, thermal and board sensors.
  7. Create the process table, then start the PIT and verify it ticks.
  8. Start APs through INIT-SIPI-SIPI (they idle until scheduling is enabled).
  9. Initialise PS/2, USB HID and the VGA shadow buffer.
  10. Inflate the command pack into /ramfs; start the WM and the first frame.
  11. Probe the NIC, restore retained network config, start the kworker.
  12. Mount FAT devices; call wm_server_boot_ready() so the WM spawns the first terminal; run DHCP if needed.
  13. Enable scheduling on the APs and enter the kernel idle loop.

The boot trace lines written along the way (boot_trace, boot_val) go to the framebuffer console and COM1, so a machine without serial still shows where a boot stopped. The WM disables the boot console when it attaches; bootlog prints the saved text.

Failure modes to know

  • No VBE mode. The legacy stage cannot produce a framebuffer; the kernel may start headless or the boot stops in the stage.
  • Pack larger than the low gap. The legacy path rejects a compressed pack above PACK_LOW_MAX. UEFI and kexec can carry more.
  • PIT not ticking. kernel_main prints *** PIT NOT TICKING *** and halts; no process scheduling is possible.
  • UEFI Secure Boot. The unsigned BOOTX64.EFI is rejected before any NebOS code runs.
  • Stale boot info. The checksum makes an invalid 0x500 block read as absent rather than as a bogus pack or RSDP.
