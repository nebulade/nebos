NebOS 0.2.0 · Architecture notes

One small OS, from boot sector to browser.

NebOS is a from-scratch, freestanding 32-bit x86 operating system written in C and assembly. It targets a first-generation Pentium, boots from a floppy, a USB disk or x86-64 UEFI firmware, and carries its own scheduler, filesystems, window manager, TCP/IP stack and ring-3 command pack.

i586 · 32-bit freestanding · no libc BIOS + UEFI serial + net hot reload

The system stack

Almost everything is built in-tree: the boot sectors, the physical memory manager, the scheduler, the FAT driver, the USB host controllers, the TCP client, the TLS implementation and the applications. The only runtime contract with the outside world is the PC firmware and the x86 instruction set.

At a glance

8 CPUs

BSP plus up to seven APs, discovered through ACPI/MADT and started with INIT-SIPI-SIPI. Without ACPI the machine stays on the uniprocessor path.

64 process slots

Kernel threads and ring-3 processes share a sparse, stable PCB table. Kernel threads are pinned to the BSP; user work can run on any AP.

8 windows

Terminal and canvas windows are composited by the window manager, with per-window RGB565 canvases mapped into the owning process.

8 MB rootfs

The command pack travels as a compressed NBROOT1 image and is inflated into a read-only ramfs at boot. Runtime replacement needs no reboot.

Design constraints

The unusual parts of the architecture follow from a few hard rules. They explain why the code uses fixed low-memory blocks, why the kernel is linked below 0x7F000, and why so much care goes into keeping the kernel image small.

  • Freestanding C. No libc, no malloc, no printf, no external runtime. Formatting and allocation are in-tree.
  • i586 baseline. Builds use -march=i586 -mno-sse -mno-sse2 -mno-mmx; SSE2 drawing paths are probed at runtime.
  • Identity-mapped paging. Physical and virtual addresses are equal. There is no per-process address space or isolation.
  • 128 MB physical ceiling. The frame bitmap covers 128 MB; anything above that is unmapped.
  • Hardcoded low memory. Boot info, the E820 map, the framebuffer block and the AP trampoline have fixed addresses that every boot path must honour.
  • No firmware runtime. reboot and poweroff use legacy ports; UEFI runtime services are not called after ExitBootServices.

Fresh memory is not zeroed. mm_alloc_page and kmalloc return whatever RAM contained. Every structure read before it is written must be cleared on allocation; QEMU hides this because its RAM starts clear.

Reading path

If you are new to the tree, follow the machine through a boot:

  1. Boot — the real-mode stage, the UEFI loader and the 0x500/0x600 handoff contract.
  2. Memory — the fixed low-memory map and the 4 KB frame allocator it feeds.
  3. CPU & scheduling — interrupt setup, the CFS-lite scheduler and the big kernel lock.
  4. Drivers — how storage, USB, input and sensors are discovered.
  5. Graphics — the shadow buffer, compositor and ring-3 canvas model.

The remaining pages cover the filesystem and command-pack pipeline, the network stack, the ring-3 ABI and the development workflow.
