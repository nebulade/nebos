Memory & paging

A fixed ladder and a 4 KB frame allocator.

NebOS identity-maps physical RAM with 4 MB pages and hands out 4 KB frames from a bitmap. A small set of low-memory addresses is fixed by the boot path and the ABI; everything else — process stacks, window canvases, the ring-3 heap and the rootfs copy — is dynamic.

Physical memory

The real-mode stage probes INT 15h E820 and writes the map to 0x1000; the UEFI loader synthesises the same structure from GetMemoryMap. mm.c starts with every page marked used, frees the E820 “usable RAM” ranges, then reserves the regions the kernel already owns.

Paging & caching

paging.c builds an identity map of RAM with 4 MB pages through CR4.PSE, adds the framebuffer's LFB range, and enables CR0.PG and CR0.WP. Before switching, it clears translation controls a BIOS protected-mode call can leave behind: CR4.PAE/PGE/LA57/PCIDE/SMEP/SMAP and EFER.LME.

  • Identity map. Physical and virtual addresses are equal. Page-directory entries are shared with every process.
  • Kernel stacks mapped everywhere. Each process gets a page directory cloned from the kernel identity map, so CR3 can switch while still running on the old kernel stack.
  • LFB is uncacheable by default. If mtrr_set_wc() successfully covers the framebuffer, the LFB pages are mapped cacheable so the shadow-buffer flush can write-combine.
  • No process isolation. There is one address space with per-process page directories only for mappings; a wild ring-0 or ring-3 pointer can reach any mapped physical page.

There is no cross-CPU TLB shootdown. MMIO mappings for another CPU's running process rely on not-present TLB entries not being cached; normal process teardown is unaffected because no two processes share an address space.

NVIDIA ION special case. On the ION the framebuffer is stolen DRAM and the VBE LFB is a BAR3 window into it. The BIOS leaves a 512 MB uncacheable MTRR over the PCIe apertures, so nvidia.c locates the framebuffer in the stolen VRAM and writes through that alias once a WC MTRR covers the stolen range. Everything else keeps the uncacheable LFB.

Frame allocator

mm.c keeps one bit per 4 KB page for the whole 512 MB window. The bitmap is not IRQ-safe; callers save and disable interrupts around allocations. The allocator returns:

  • mm_alloc_page() — one zero-address-ambiguous page (physical address 0 means failure).
  • mm_alloc_pages(n) — n contiguous pages.
  • mm_free_page() / mm_free_range() — release a page or a page-aligned boot reservation.

At boot, mm_init reserves the low 1 MB, the 8 MB VGA shadow region, any LFB that happens to live below 512 MB, and the boot-time rootfs pack. The pack reservation is released by ramfs_init after it copies/inflates the pack into fresh pages.

Fresh pages are not zeroed. Structures whose fields are read before being written must be cleared explicitly; clear_proc() in process.c exists because a stale cr3 faulted on real hardware while QEMU's cleared RAM hid the bug.

kmalloc

kmalloc.c is a power-of-two heap allocator on top of the frame allocator. It is intentionally simple: allocation rounds to a size class, free lists are per class, and large objects become contiguous page runs. PCBs, command context and sys_fs.c file loads use it.

The kernel heap is separate from userspace. Ring-3 processes get one anonymous arena through SYS_MEM_ALLOC, SYS_MEM_GROW and SYS_MEM_FREE; commands manage it with malloc/free from libc/malloc.c. The syscalls are the backend in libc/ucmd_mem.c and are not called by application code.

Ring-3 memory

A ring-3 ELF is linked at 0x40000000. The image and its 8-page user stack live in a 2 MB window ending at 0x40200000. The kernel window server maps a window's RGB565 back buffer at 0x50000000, and the anonymous heap starts at 0x60000000.

RangeSizeContents
0x40000000–0x402000002 MBELF segments, user stack top at 0x40200000 (8 pages, grows down)
0x50000000–0x504000004 MBOne window canvas mapping (RW, per window)
0x60000000–0x62000000up to 32 MBAnonymous heap; initial allocation zeroed, growth pages are not

Ring-3 commands treat that arena as a real heap: libc/malloc.c maps 64 KB on first use, grows in page-rounded steps with 64 KB slack, and uses boundary-tag blocks with a first-fit free list and immediate coalescing. heap_reset() discards everything and unmaps the arena; the browser calls it on navigation, so page-scoped allocations (body, rules, image bitmaps and decode arenas) go back to the frame allocator. A single allocation near 32 MB fails because block headers count against the same cap.

Kernel stacks are 4 KB pages from the frame allocator, with an 8-stack static fallback pool in BSS. The idle/bootstrap context uses the in-image 8 KB .stack section. The user stack is separate: 8 pages just below 0x40200000.

Rootfs pack lifetime

  1. The boot path places the gzip pack in RAM: the legacy stage copies it directly to 0x900000 with INT 15h AH=87h, UEFI at the top of RAM below 512 MB, kexec in its staging buffer.
  2. mm_init reserves [pack_addr, pack_addr + pack_size) so the frame allocator cannot reuse it.
  3. ramfs_init takes a private page-allocated copy, validates the NBROOT1 header and inflates the pack into it.
  4. mm_free_range releases the boot region when it is above the VGA shadow reserve. The private copy lives until ramfs_replace or reboot.

The ramfs holds at most 128 files and 8 MB of decompressed pack. A larger pack fails to load rather than partially mounting.

Limits & leaks

  • No per-process address spaces. Paging is identity-mapped; there is no memory protection between processes.
  • 512 MB ceiling. Physical memory above 0x20000000 is unmapped. A wild pointer there is an instant #PF.
  • User page leak on reap. Killing a ring-3 process frees its kernel stack and page directory but not all user pages mapped into it; a few pages leak per command run.
  • Kernel heap fragmentation. kmalloc's power-of-two size classes make long-running mixed-size kernel allocation wasteful; ring-3 commands use the separate first-fit libc heap described above.
  • No TLB shootdown. Cross-CPU mapping changes rely on not-present entries not being cached.
